  Warum CPU >60% und RAM 26 GB?

  Täter: Der ML-Service läuft gerade Stage-2-Enrichment auf mehreren Aktivitäten

  In pg_stat_activity laufen 6 aktive PostgreSQL-Prozesse — 5 davon seit >4

  WITH route AS (
      SELECT track_full AS geom FROM activity_tracks WHERE activity_id = $1
  )
  SELECT DISTINCT ON (ww.osm_id) ww.osm_id, ww.name, ww.waterway,
         ST_Distance(route.geom::geography, ww.geom::geography),
         ST_Intersection(ST_Buffer(...), ww.geom)
  FROM osm_waterways ww, route
  WHERE ST_DWithin(route.geom::geography, ww.geom::geography, $2)

  Das ist das water.py-Modul (Gewässer-Erkennung aus Stage-2). Es führt
  PostGIS-Geo-Berechnungen gegen 1,28 Mio. Wasserweg-Geometrien durch — sehr
  CPU-intensiv. Die 5 Queries laufen parallel (per-User max-2-Semaphore, aber
  mehrere User oder Batches).

  Der 6. aktive Prozess ist das stops.py-Modul (Gastro-/Stop-Erkennung).

  ---
  Geht der RAM-Verbrauch wieder runter?

  Jein:

  - CPU geht deutlich runter sobald das Stage-2-Enrichment fertig ist (die 5+
  Wasserweg-Queries). Das kann noch ein paar Minuten dauern (laufen schon 4+
  Minuten).
  - RAM: PostgreSQL cached sehr aggressiv — die OSM-Tabellen (~62 GB raw) werden
   so weit wie möglich im Shared Buffer gehalten. Von den 26 GB belegtem RAM ist
   ein großer Teil Linux Page Cache (die buff/cache-Zeile zeigt 27 GB). Das gibt
   Linux bei Bedarf sofort frei. Der "echte" Verbrauch ist die used-Zeile
  abzüglich des Caches — tatsächlich verfügbar sind noch 17 GB. Nach Ende des
  Enrichments sinkt der Page Cache etwas, aber PostgreSQL hält populäre Daten
  gerne im RAM.

  Kurz: CPU geht runter, RAM bleibt bei ~20 GB Basisverbrauch (Ollama-Modelle +
  PG-Buffer).

● Jetzt habe ich alle Fakten. Hier die vollständige Analyse:

  ---
  1. Warum ist OSM 62 GB statt 5 GB?

  Dreifacher Effekt:

  A) PBF ist stark komprimiert — Die 5 GB DACH-Datei ist protobuf+zlib
  komprimiert. Unkomprimiert sind die Rohdaten schon ~25–30 GB.

  B) osm2pgsql importiert ALLES — Die planet_osm_nodes-Tabelle enthält 569 Mio. 
  Knoten — das ist buchstäblich jeder einzelne GPS-Punkt in DACH, nicht nur die
  für uns relevanten. osm2pgsql braucht diese während des Imports zum Auflösen
  von Ways und Relations. Danach sind sie im Wesentlichen totes Gewicht:

  ┌──────────────────┬───────┬───────────┬───────┬────────────────────────┐
  │     Tabelle      │ Daten │   Index   │ Total │         Zweck          │
  ├──────────────────┼───────┼───────────┼───────┼────────────────────────┤
  │ planet_osm_nodes │ 26 GB │ 12 GB     │ 38 GB │ osm2pgsql-interne      │
  │                  │       │ B-Tree    │       │ Struktur               │
  ├──────────────────┼───────┼───────────┼───────┼────────────────────────┤
  │ planet_osm_ways  │ 18 GB │ 4,3 GB    │ 22 GB │ osm2pgsql-interne      │
  │                  │       │           │       │ Struktur               │
  ├──────────────────┼───────┼───────────┼───────┼────────────────────────┤
  │ planet_osm_rels  │ 635   │ 599 MB    │ 1,4   │ osm2pgsql-interne      │
  │                  │ MB    │           │ GB    │ Struktur               │
  └──────────────────┴───────┴───────────┴───────┴────────────────────────┘

  Der 12 GB-Index auf planet_osm_nodes ist ein B-Tree über 569 Mio. node-IDs —
  normal für PostgreSQL, aber massiv.

  C) PostGIS-Geometrien sind teurer — Eine geography(LineString) in PostGIS
  braucht deutlich mehr Speicher als rohe Koordinatenpaare, da WKB-Encoding +
  GIST-Indizes dazukommen.

  ---
  2. Warum 1,8 GB activity_streams?

  Das ist völlig normal und erklärbar:

  - 5.469.377 Zeilen / 789 Aktivitäten = Ø 6.932 Datenpunkte pro Aktivität
  - Ø Aktivitätsdauer: ~3,25 Stunden (11.725 Sekunden) — lange
  Fahrradtouren/Wanderungen
  - 17 Spalten (lat, lng, altitude, speed, distance, HR, power, cadence, temp,
  respiration, stress, ground_contact, vertical_osc, stance_percent,
  L/R-balance) = ~91 Bytes/Zeile netto
  - 5,47 Mio × 91 Bytes = ~498 MB Nutzdaten + PostgreSQL Overhead + Indexes =
  1,8 GB macht Sinn

  Das Problem: Alle 338 TimescaleDB-Chunks sind unkomprimiert.
  TimescaleDB-Komprimierung ist nicht aktiviert.

  ---
  3. Komprimierungspotenzial

  Sofortiger Riesenhebel: planet_osm_nodes/ways/rels löschen

  Diese drei Tabellen = ~61 GB und werden nach dem osm2pgsql-Import nicht mehr
  benötigt, solange du keinen weiteren osm2pgsql-Re-Import machst. Alle
  tatsächlich benötigten Daten sind bereits in osm_waterways, osm_amenities,
  osm_forests etc. extrahiert. Löschen wäre ohne Performanceverlust für die App
  — nur wenn du OSM-Daten neu importieren willst, bräuchtest du sie wieder (aber
   dann werden sie ohnehin neu erstellt).

  TimescaleDB-Komprimierung auf activity_streams

  TimescaleDB kann Zeitreihendaten typisch 10–40× komprimieren (Columnar
  Storage, Delta-Delta-Encoding für Timestamps, Gorilla-Encoding für Floats):

  ┌──────────────────────────────────────┬──────────┐
  │               Szenario               │ Ergebnis │
  ├──────────────────────────────────────┼──────────┤
  │ Jetzt (unkomprimiert)                │ 1,8 GB   │
  ├──────────────────────────────────────┼──────────┤
  │ Nach Komprimierung (10× konservativ) │ ~180 MB  │
  ├──────────────────────────────────────┼──────────┤
  │ Nach Komprimierung (40× optimal)     │ ~45 MB   │
  └──────────────────────────────────────┴──────────┘

  Performanceverlust: Queries auf komprimierten Chunks sind minimal langsamer
  (~5–15%), da Dekomprimierung nötig ist. TimescaleDB dekomprimiert lazy per
  Chunk. Für aggregierte Queries (Heatmap, Charts) kann es sogar schneller sein
  wegen weniger I/O. Einziger Nachteil: INSERT auf bereits komprimierte Chunks
  geht nicht direkt — man müsste erst dekomprimieren (kein Problem wenn Chunks
  alt genug sind → Komprimierung nur auf Chunks >7 Tage).

  heatmap_points (1 GB, 4,7 Mio Einträge)

  Diese werden dynamisch aus activity_streams berechnet. Die Frage ist: Muss das
   materialisiert sein? Alternativ könnten Heatmap-Punkte beim ersten Aufruf
  berechnet und gecacht werden, statt persistent gespeichert. Das spart 1 GB.

  5. Performance-Optimierungen (ohne Komprimierung)

  Hier ist der interessanteste Fund aus den Daten:

  Kritisch: GIST-Indexes werden NIE benutzt (idx_scan = 0)

  osm_waterways_geom_idx   → 0 Scans
  osm_amenities_geom_idx   → 0 Scans
  osm_peaks_geom_idx       → 0 Scans
  osm_lifts_geom_idx       → 0 Scans

  Ursache: Die Spalten sind als geometry gespeichert, der Index ist ein
  geometry-GIST-Index. Die Queries casten aber zu geography:

  WHERE ST_DWithin(route.geom::geography, ww.geom::geography, 500)

  PostgreSQL kann den geometry-Index für eine geography-Query nicht nutzen — das
   ist ein Type-Mismatch. Ergebnis: Sequential Scan über 1,27 Mio. 
  Wasserweg-Geometrien bei jeder Stage-2-Enrichment-Anfrage. Das erklärt die >4
  Minuten die du gerade siehst. Die Lösung wäre ein geography-Index: CREATE 
  INDEX ON osm_waterways USING gist (geom::geography) — aber du hast gesagt nur
  informieren.

  work_mem zu niedrig für Geo-Queries

  work_mem = 7 MB — sehr niedrig. PostGIS-Operationen wie ST_Intersection,
  ST_Buffer, ST_Union auf großen Geometrien brauchen deutlich mehr (64–256 MB
  empfohlen). Bei zu wenig work_mem spilled PostgreSQL auf Disk. Für 44 GB RAM
  wäre 64–128 MB sinnvoll.

  shared_buffers vs. effective_cache_size-Diskrepanz

  shared_buffers:      ~11 GB (gut, ~25% RAM)
  effective_cache_size: ~33 GB (korrekt)
  Das ist gut konfiguriert.

  health_daily_summary: 351 Chunks für ~2 Jahre Daten

  Das ist ein zu kleines Chunk-Intervall. 351 Chunks für health-Daten bedeutet
  TimescaleDB erstellt sehr viele Mini-Partitionen → erhöhter Planner-Overhead
  bei aggregierten Queries.
